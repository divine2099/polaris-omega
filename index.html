Polaris Omega

a cross-chain arbitrage engine with a solver-grade execution layer

Finds price differences between decentralised exchanges, on one chain and between chains, and checks every trade exactly against the chain before sending it.

Its edge is between chains, where the winner is whoever prices both sides correctly and has inventory in place, not whoever is first into the block.

Moves money only through each exchange's own entry functions. Never by sending it somewhere and hoping.

Built by Jamike Divine, a solo builder working with an AI system. Proven on a public test network; not yet traded with real money.

#01what_it_isplain english

The same asset is often priced slightly differently in two places at the same moment. Polaris Omega has two engines for that.

The first engine works inside one chain. It buys on one exchange and sells on another in a single transaction that either completes or does nothing, with the money borrowed and repaid inside that same transaction. It needs no capital of its own. But on one chain it is a race: whoever lands first in the block takes the trade, and that race is decided by hardware and position. This engine is the entry point and the steady base, not the edge.

The second engine works between chains, and that is where the edge sits. No loan can span two chains, so this needs real capital resting on each side. In exchange, it does not need to be first. The gaps it is designed to hunt last seconds to minutes rather than one block, so it competes on pricing both chains correctly, checking every leg exactly and moving inventory cheaply. Fewer players can do that, because it takes capital, risk control and infrastructure on several chains at once.

The solver layer is what makes the second engine work. A solver fills other people's orders on intent-based venues and moves assets between chains for a fee. Polaris Omega already speaks those venues' order formats natively, and its cross-chain engine uses them to move its own inventory. With enough inventory it can also fill other people's cross-chain orders using the same capital, so moving its own money becomes a source of fees instead of a cost. That is why it is designed as a hybrid of arbitrageur and solver. The solver side is built and switched off today, because it needs that capital to front fills.

The architecture is the edge, so this page says what the system does and what it has done, and not how it decides what to trade.

#02how_its_builtfull architecture →

inside the node

Most bots ask a node for data over the network and are always a little behind. On Ethereum, Base and Optimism this runs as an extension inside the node software itself. On Arbitrum and BNB Chain, whose nodes have no extension slot, it runs beside the node on the same machine and reads its live feed, producing the same signals.

every trade simulated exactly

Before anything is sent, the trade is run against the chain's current state with the same virtual machine the chain uses. If the result is off by the smallest unit, it is not sent.

one small contract, money through doors

A single contract with no stored state carries out each trade. Value only moves through an exchange's own entry functions, enforced when the trade is built rather than reviewed afterwards.

two keys and a scoped vault

Single-transaction trades take one key. Anything that settles in two parts needs a second, independent signer with its own rules. Inventory sits in a Safe, and the trading key gets only a narrow role over it.

every claim names its check

A ledger records every assumption the system rests on, marked verified, unverified or falsified, with the test that decides it. The tools are built to tell "nothing was there" apart from "I could not look", because most tools print the same silence for both.

A Safe with a tightly scoped role took one trade of its inventory exactly as simulated. Every attempt to step outside the role was refused by the role itself.

Both signers up, a trade planned and simulated as its two transactions, handed to the sender. The staleness check stopped it because the machine had fallen too far behind the chain. Nothing was signed. That is the right outcome, and it says what the next step is.

not yet: no trade on a real network with real money, no live record of returns, and no forecast of one on this page.
#04blockersnone of them code
CRIT
the machine

The development machine cannot host a node, so it reads the chain over the network. On Base, a block every fifth of a second, that leaves it ~200 blocks behind against a 10-block window. The check is doing its job and has no setting to loosen. The fix is a bare-metal box beside a node: about $456/month for one chain, ~$1,600/month for all of them.

HIGH
chain access

A paid plan at a hobby tier. Enough to test; a live run would spend more in a day than it allows. A private endpoint removes this.

HIGH
the AI bill

One person building with an AI coding system, said plainly. The plan tier sets the pace. A better plan is the cheapest way to make everything move faster.

CRIT
capital

The single-chain engine needs only gas, and that is not where the edge is. The cross-chain engine, the solver fills and later market making all need working capital on each chain, to hold inventory and to front fills. That part is built, planned end to end on live data, and stops at exactly this point.

#05roadmapno dates until the machine exists
  1. a node machine for one chain. The system moves beside a node and stops falling behind.
  2. the first real-network trades, single-chain first, with small balances declared in advance and every transaction published net of gas.
  3. the cross-chain engine with working capital, starting with inventory held on two chains in a vault the system cannot empty, every leg co-signed by two keys.
  4. the solver side, filling other people's cross-chain orders with that same inventory, starting with the venue that needs no one's permission.
  5. the other chains, one at a time, each with its own record.
